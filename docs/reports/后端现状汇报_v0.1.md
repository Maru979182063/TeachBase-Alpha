## 5. 当前实现层面的真实情况

### 5.1 本地运行态

本次检查时，本地 `8787` 与 `8790` 都无法访问，且未看到对应监听端口。这说明：

- 当前 demo 栈此刻并未处于运行状态
- 现状汇报不能按“服务已长期稳定运行”来表述

### 5.2 当前后端仍以 mock API 为主

从 `tools/mock_workbench_api_server.mjs` 看，当前导出接口仍是：

- 本地 HTTP 服务
- 基于文件系统沉淀导出产物
- 通过同步方式调用 Python 导出脚本

这说明它更接近：

- demo 接口
- 工具编排层

而不是正式的任务编排后端。

### 5.3 数据库尚未进入主流程

本次仓库检查没有发现已经接入主流程的：

- `Postgres`
- `Redis`
- ORM
- 正式任务事实源
- 正式队列投递

所以当前状态仍然是：

- 文件产物驱动已经有雏形
- 数据库驱动的后端主流程还没有真正落地

### 5.4 审核与发布还不是正式主流程

虽然设计里已经强调人工审核的重要性，但当前实现仍更像：

- 先生成产物
- 再由人查看或导出

还没有真正进入：

- revision
- review_task
- publish
- 回滚与追溯

这一套正式流程。

## 6. 当前最关键的差距

### 6.1 设计正确，但实现还没落到数据库事实源

这是当前最大的阶段性差距。  
现在的主要问题不是“方向错了”，而是“还没把正确结构变成真正的后端事实模型”。

### 6.2 还不能保证重跑安全

如果现在就开始大量重跑、局部修订和多人审核，最容易出的问题是：

- 人工调整被覆盖
- 导出物追溯不上游版本
- 不知道哪一版结构树参与了生成
- 夜间批处理和白天审核互相干扰

### 6.3 组件层还没真正成为稳定主对象

项目里已经有“页图、裁片、组件切分”的概念，但它们还没有在主模型里成为稳定业务对象。  
这会影响后续：

- 节点重组
- 题目回溯
- 公式图片绑定
- 局部重跑

### 6.4 学科插件边界还停留在概念层

当前还没有真正的：

- 插件输入版本化 contract
- 插件输出 artifact contract
- Materializer 统一落库

如果直接往前堆功能，后面很容易变成每个学科脚本各自改数据。
