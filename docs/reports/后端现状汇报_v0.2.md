# 后端现状汇报 v0.2

更新时间：2026-06-23

## 1. 本轮完成范围

本轮已按“验证版事实源 + 题库留存 + 跨讲义检索 + Component 局部重跑 + 任务恢复”的目标推进，重点不是补大而全 ERD，而是把现有 `8790` 服务推进到一套可以继续演化的验证骨架。

已落地的核心点：

1. `8790` 运行时接口已切到 `Store interface`，不再直接绑死在单个状态文件读写逻辑。
2. 保留 `FileStore` 作为当前可运行模式，并新增 `PostgresStore` 骨架。
3. 补齐验证版 migration，覆盖 lesson import、task_projection、question_bank、material_build、component rerun、publication、run/job/artifact/recovery 这批关键表。
4. 修正 `approve != publish`。
5. 修正 artifact 语义，rerun 不再把历史发布链路直接打成失效。
6. 新增 LessonDraftBundle 导入、跨讲义检索、题库留存、讲义落版、组件局部重跑、任务恢复相关 API。
7. 已实际跑通一轮接口验证脚本，不是只停留在代码层。

## 4. PostgresStore 实现范围

本轮不是把业务完全改成“直接 SQL 业务层”，而是先把 Postgres 验证版骨架搭起来：

1. 新增 `pg` 依赖。
2. 新增 validation migration。
3. 新增 `PostgresRuntimeBackboneStore`。
4. 采用“状态快照 + 验证表镜像”方式保留当前业务逻辑，避免本轮就把全部行为重写成 SQL 版本。

当前 `PostgresStore` 的定位：

- 可以作为下一轮切库的承接层。
- 会把当前 runtime state 同步到 validation tables。
- 需要真实 `DATABASE_URL` 才能实际启动。

当前没有做的事：

- 本机未接入真实本地 Postgres 实例做 live 验证。
- 还没有把业务查询完全改成“直接从 Postgres 归一化表读”。

## 6. approve / publish 行为

当前已修正为：

1. `POST /api/runtime/review-tasks/:id/approve`
   只把 `review_task` 标记为 `approved`，并把 `lesson_revision` 标记为 `approved`。
2. `approve` 不再直接改 `lesson.published_revision_id`。
3. 新增 `POST /api/runtime/lessons/:lessonId/publish`。
4. 只有 `publish` 才会创建 `publication` 并切换 `lesson.published_revision_id`。

## 7. artifact stale 语义修正

当前已修正：

1. `artifact` 增加 `integrity_status` 和 `logical_status`。
2. rerun 不再批量把历史 `source_tree_snapshot` / `task_bundle` / `reviewed_publishable_bundle` 标成 `stale`。
3. 历史 publication 引用链不再因为 rerun 被直接破坏。

当前仍是验证版：

- 还没有单独再引入 `artifact_binding` 一类更细的发布绑定层。

## 8. LessonDraftBundle 导入

已新增：

- `POST /api/runtime/imports/lesson-draft-bundles`

当前导入行为：

1. 接收 bundle。
2. 计算 `content_hash`。
3. 生成 import run / job / artifact。
4. 写入 `lesson_revision.bundle_jsonb`。
5. 重建 `task_projection`。
6. 创建 `review_task`。
7. 可选写入 question bank candidate。

当前已验证：

- 同 `bundle_id + content_hash` 重复导入会幂等返回。
- 同 `bundle_id` 但内容变化会生成新 revision。

## 9. task_projection 跨讲义检索

## 10. question_bank 留存

已新增：

- `POST /api/question-bank/items`
- `GET /api/question-bank/search`

当前能力：

1. 可从 `task_projection` 收录进题库。
2. 题库题有稳定 `question_bank_item`。
3. 每次编辑或新收录都形成 `question_bank_item_revision`。
4. 来源链记录在 `question_bank_source_link`。

## 11. material_build / material_item

已新增：

- `POST /api/material-builds`
- `POST /api/material-builds/:id/items`
- `POST /api/material-builds/:id/export`

当前能力：

1. 创建讲义落版配置。
2. 把固定题库 revision 放进讲义落版项。
3. 导出时登记 `run/job/artifact`。

## 12. Component 局部重跑

已新增：

- `POST /api/runtime/components/:componentId/rerun`
- `GET /api/runtime/components/:componentId/revisions`
- `GET /api/runtime/component-patches/:patchId`
- `POST /api/runtime/component-patches/:patchId/accept`
- `POST /api/runtime/component-patches/:patchId/reject`

当前流程：

1. 选中 component。
2. 发起 rerun。
3. 生成新的 `component_revision`。
4. 生成 `component_patch_candidate`。
5. 人工 accept / reject。
6. accept 后触发新的 `lesson_revision`，并同步新的 `review_task`。

当前仍是验证版：

- 现在是固定 bbox 的内容级 rerun。
- 还没有做自动拆分、合并、通用依赖传播 DAG。

## 13. run / job 恢复能力

当前已落地：

1. `job_attempt` 已进入状态模型。
2. 新增 `recoverJobs()` 逻辑。
3. 服务读取状态时会扫描 `running` 且 heartbeat / timeout 超时的 job，并回收为 `retry_wait`。
4. 新增手动触发接口：
   - `POST /api/runtime/jobs/recover`

## 16. 尚未完成事项

本轮还没做完的点，我不把它写成“已完成”：

1. `PostgresStore` 还没有接真实本地或 VPS Postgres 做 live 联调。
2. 现在 `PostgresStore` 还是“快照 + 验证表镜像”，不是最终直读直写归一化表版本。
3. `material_build/export` 还不是最终完整排版引擎。
4. component rerun 还没有做自动拆分 / 合并 / 通用增量传播。
5. 还没有完整跑你附文里列出的 20 项全量正式测试矩阵，只跑了当前这轮关键闭环验证。
6. 8792 的演示 sidecar 还没同步到这轮接口层。

## 17. 结论

这轮不是“目标版后端”已经结束，但已经从“只有 file demo 和导出挂接”推进到：

- 有统一 Store 接口
- 有 Postgres 验证版承接骨架
- 有 lesson import / publish / search / question bank / material build / component rerun / recovery 的最小闭环
- 原有 `8790` 导出链继续可用

下一轮如果继续推进，建议优先顺序：

1. 用真实 Postgres 跑通 `PostgresStore`
2. 补齐更正式的测试矩阵
3. 收紧导入 schema 校验
4. 细化 publication 与 material_build 的正式导出绑定
