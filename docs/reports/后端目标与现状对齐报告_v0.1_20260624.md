# 后端目标与现状对齐报告 v0.1

更新时间：2026-06-24

## 1. 报告目的

本报告用于对齐当前后端实现与既定目标范式，重点回答三个问题：

1. 当前后端是否支撑“题目是基础内容对象，讲义骨架是主结构对象，知识点是语义映射层”的设计方向。
2. 现有运行骨架、验证表和接口实现与目标范式之间还有哪些偏差。
3. 下一步应继续沿用当前范式，还是需要调整底层模型。

## 2. 目标范式

当前项目更合理的目标范式，不是“只有题目是数据，其他都是标签”，而是四层分工：

### 2.1 题目层

- `task / task_revision` 是基础内容对象。
- 题目承载题干、答案、解析、题型、难度、风险、学科扩展等内容。
- 题目应有稳定身份和版本，不应只作为某次导入的临时结果存在。

### 2.2 讲义骨架层

- `source_tree / source_node_revision` 是主结构对象。
- 这一层表达讲次、模块、例题区、训练区、知识主干等课堂组织结构。
- 题目的主归属应挂在骨架节点下，而不是直接挂在知识点名称或字符串标签下。

### 2.3 知识点语义层

- `checkpoint_catalog / checkpoint_node` 是知识点目录。
- `source_node_checkpoint_link` 表示骨架节点的默认知识点映射。
- `task_checkpoint_override` 表示少量特殊题的单题覆盖映射。
- 这一层用于表达语义归类和检索，不替代讲义骨架。

### 2.4 查询与使用层

- `task_projection` 是查询投影，不是主事实源。
- `question_bank_item` 是稳定题库资产。
- `publication` 是正式发布边界。
- `material_build / material_item` 是后续教师使用端和搭板层的预留方向。

## 3. 目标状态的核心原则

从业务和后续扩展角度看，这套范式应满足以下原则：

1. 题目是基础内容实体，但不是唯一结构事实源。
2. 讲义骨架是题目的主挂载位置，承担课堂节奏和结构组织。
3. 知识点属于语义映射层，默认跟节点走，少量题目再单独覆盖。
4. 发布态和审核态分开，教师侧后续只能消费已发布内容。
5. `task_projection`、题库检索、导出、教师搭板都应建立在已发布数据之上，而不是直接读写底层修订对象。

## 4. 当前后端现状

结合现有文档、迁移脚本和运行代码，当前后端状态可以概括为：

### 4.1 已经成形的部分

- `8790` 服务已通过 `Store interface` 解耦，具备继续演化条件。
- 当前保留 `FileStore` 可运行模式，并补了 `PostgresStore` 骨架。
- 已有 `approve != publish` 的边界拆分，发布语义方向正确。
- 已补 validation migration，覆盖 `task_projection`、题库、发布、导出、运行恢复等关键表。
- 已有 `question_bank`、`publication`、`material_build` 这些后续使用层对象的雏形。
- 运行骨架已支持 `run / job / artifact / recovery`，为异步导出和后续扩容留出空间。

### 4.2 当前实际运行方式

- 当前本地运行仍以 `runtimeMode = file` 为主。
- `PostgresStore` 仍是“状态快照 + 验证表镜像”模式。
- 当前验证层重点是把流程跑通，不是完整切换到归一化数据库直读直写。

## 5. 对齐情况判断

### 5.1 已对齐的部分

从完整设计稿看，底层模型与目标范式是对齐的：

- `source_node_revision` 已被定义为讲义骨架节点实体。
- `task_revision` 已被定义为题目修订实体，并明确引用 `source_node_revision_id`。
- `source_node_checkpoint_link` 和 `task_checkpoint_override` 已明确区分“默认映射”和“单题覆盖”。
- `task_subject_ext` 已为后续学科插件扩展留出口子。

也就是说，设计理念并没有跑偏，当前模型不是“纯题目中心 + 扁平标签”的错误方向。

### 5.2 半对齐的部分

当前 validation schema 与 runtime 投影层，只对齐到了中间状态：

- validation migration 中已有 `task_projection`、`question_bank_item`、`publication`、`material_build` 等投影或使用层表。
- 但还没有把完整的 `source_node_revision / source_node_checkpoint_link / task_checkpoint_override` 作为 validation 主路同步落地。
- 这意味着当前 Postgres validation 层还不能完整承接“骨架主挂载 + 知识点继承”的范式。

### 5.3 未完全对齐的部分

当前 runtime 实现与目标范式的主要偏差有三点：

1. `task_projection` 当前承担了过多事实源语义。  
   它本应只是查询投影，但目前在验证链路里已经承接了较多结构和标签信息。

2. 当前知识点计算更偏“单题 override 主路”。  
   运行代码里虽然存在 `sourceNodeCheckpointLinks`，但 `getCheckpointCodesForTaskRevision()` 目前主要从 `taskCheckpointOverrides` 取值，尚未形成稳定的“节点默认继承 + 单题覆盖”逻辑。

3. 导入流程里题目挂骨架已经成立，但知识点仍主要跟题走。  
   `hydrateRevisionFromBundle()` 已经会把题目挂到 `source_node_revision_id`，说明题目主挂载方向是对的；但 `checkpoint_codes` 仍主要以单题方式写入 `taskCheckpointOverrides`，导致语义层偏向“题目自带 checkpoint 标签”。

## 6. 结论

### 6.1 是否支撑

结论是：支撑，但当前是“设计支撑，运行实现部分支撑”。

换句话说：

- 完整设计稿已经支撑目标范式。
- 当前后端现状没有走错路。
- 但验证实现还没有把这套范式完全落实到底。

### 6.2 是否需要修改

不需要推翻当前架构哲学，也不需要改成“只有题目是事实源，骨架和知识点都是标签”的模型。

真正需要做的是：

- 保持当前双实体结构不变：
  - 题目是内容实体
  - 讲义骨架是结构实体
  - 知识点是语义映射层
- 将 runtime 与 validation schema 继续向这个目标范式收敛
- 明确把 `task_projection` 限定为只读投影，而不是主事实层

## 7. 最小修正建议

在不推翻现有后端的前提下，建议只做以下几项最小修正：

### 7.1 把结构层正式带入 validation / Postgres 主路

建议把以下对象补进 validation schema 和 Postgres 同步逻辑：

- `source_node_revision`
- `source_node_checkpoint_link`
- `task_checkpoint_override`

这样后续教师工作台、题库、导出、发布都能真正建立在结构化事实源之上。

### 7.2 调整 checkpoint 计算逻辑

建议把当前知识点读取逻辑改成：

`节点默认映射 + 单题 override`

而不是只从 `taskCheckpointOverrides` 取值。

### 7.3 明确 `task_projection` 的定位

建议在文档与代码语义上统一：

- `task_revision` 才是底层内容修订对象
- `task_projection` 只是面向搜索、题库收录和后续教师侧消费的查询投影

### 7.4 保持发布边界不动

当前 `approve != publish` 的修正方向是正确的，应继续坚持：

- 审核通过不等于正式发布
- 教师侧后续只消费 `published` 数据
- `publication` 继续作为正式边界

## 8. 对后续扩展的意义

如果继续沿用当前目标范式，并完成上述最小修正，则后续这几类扩展都还能自然承接：

1. 讲义骨架校正台
2. 题目入题库与跨讲义复用
3. 组件库与非题组件资产化
4. 教师侧基于已发布内容做选题、组合、导出
5. 多学科插件扩展

如果反过来改成“题目是唯一实体，骨架和知识点都只是标签壳”，短期实现看似更快，但后续会在以下方面持续返工：

- 跨讲义重组
- 组件复用
- 骨架校正
- 默认考点继承
- 教师版 / 学生版双视图
- 审核与发布留痕

## 9. 报告结论

当前后端现状与目标范式总体一致，方向不需要推翻。完整设计已经具备“题目作为基础内容对象、讲义骨架作为主结构对象、知识点作为语义映射层”的支撑能力。当前主要问题不在于模型思想错误，而在于 runtime 验证实现和 Postgres validation schema 仍停留在中间态：结构层和知识点继承逻辑还没有完全落到数据库与投影层。

因此，建议继续沿用当前范式，不做架构级重构；下一步应聚焦于结构层落表、默认知识点继承逻辑补齐，以及投影层语义收敛，把现有“能跑”的验证骨架继续推进成“语义一致”的后端底座。
