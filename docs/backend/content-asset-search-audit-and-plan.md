# 教学内容资产与搜索基础设施审计及实施计划

> 文档状态：讨论稿，尚未授权实施  
> 审计日期：2026-09-02  
> 审计基线：`backend/java-modulith-foundation-survey` / `d68828c334fa8a275effccc59e4c2ef9c060d5ef`  
> 覆盖范围：知识结构、标准化模块、讲义、临时内容、模型补全、模糊搜索、版本、权限与首批数据  
> 不覆盖范围：四条题目生产链内部机制、前端视觉实现、难度标准制定、生产级 OpenSearch 部署

## 1. 执行摘要

TeachBase 当前已经拥有支撑这一领域的主要地基：PostgreSQL、稳定对象身份、不可变修订、
审核状态、知识体系版本、知识点别名、文件版本、讲义草稿与快照、题目检索、题篮、审计事件
以及后台任务的锁和租约模式。现有结构没有必要推倒重建。

但当前能力仍停留在“题目、知识结构和讲义各自有一部分基础”的阶段，尚未形成完整的教学内容
资产系统：

1. 标准化模块还不是一等业务对象，文本、图片、表格、公式、思维导图和复合模块没有统一的
   稳定身份、版本、审核、引用和搜索合同。
2. 知识点目前只有精确编码或别名解析，没有面向用户的模糊搜索、层级路径排序和结果计数。
3. 讲义已有修订和不可变快照，但没有章节级搜索投影、结果高亮和版本去重。
4. 题目已有 PostgreSQL 模糊包含检索，但没有真正的相关性排序，结构化主副知识点关联尚未
   完整进入搜索。
5. 临时内容没有“先保存、自动加工、人工确认、再共享”的正式生命周期。
6. 模型补全任务、字段级建议、确认记录和失败恢复尚未建立。
7. 正式登录认证尚未接入；现有 `actorUserId` 只能用于开发门禁，不能成为生产权限凭证。

推荐采用“规范业务表 + 可重建搜索投影 + 异步语义补全”的三层结构：

- 规范业务表保存内容真相、版本、审核、来源和引用。
- PostgreSQL 搜索投影保存为搜索而展开的标题、别名、路径、正文和章节块。
- 模型只生成可追踪的字段建议，不修改原始内容、不直接发布，也不进入在线搜索请求链路。

第一阶段不引入 Elasticsearch、OpenSearch、Redis 或向量数据库。现有 PostgreSQL 的
`pg_trgm`、GIN/GiST、结构化索引和加权全文检索足以支撑 MVP。搜索模块通过稳定端口隔离，
未来出现明确容量或相关性证据后再更换实现。

## 2. 审计目标与判定标准

本次审计回答六个问题：

1. 当前后端已经能可靠保存和追踪哪些对象？
2. 临时创建的图片、表格或文本能否立即保存，并在后续方便找到？
3. 哪些信息必须由用户确认，哪些可以由程序或模型补全？
4. 知识点、标准化模块和讲义应如何分别搜索，又如何统一搜索？
5. 多版本、权限、历史引用和知识树升级时，搜索结果是否会串版或泄漏？
6. 在不提前引入重型基础设施的前提下，怎样分阶段交付并可验证？

审计中的“已支持”要求同时具备数据库结构、Java 应用合同和现有测试证据；仅存在旧表、文档
设想或原型字段不计为已支持。

## 3. 当前后端能力审计

### 3.1 已具备且可以复用的能力

| 能力 | 当前实现 | 审计结论 |
| --- | --- | --- |
| 工作区隔离 | 核心业务表使用 `workspace_id` 和组合外键 | 可复用，搜索必须继续强制工作区边界 |
| 用户业务身份 | `app_user`、`workspace_member` | 有档案和角色，没有正式认证凭证 |
| 用户教学范围 | `workspace_member_teaching_scope` | 已支持精确“学科 + 学段”组合和主范围 |
| 文件资产 | `file_asset`、不可变 `file_version` | 图片等二进制应继续引用文件版本，不放进模块 JSON |
| 来源追踪 | `source_document`、文件与题目来源证据 | 可承接模块和讲义的来源、版权与加工链路 |
| 题目身份与版本 | `question`、不可变 `question_revision` | 当前修订和审核通过修订分离，基础正确 |
| 题目审核 | 审核案例、决定、生产修订指针 | 可复用为模块审核模式，但不能直接共用题目表 |
| 知识体系版本 | `taxonomy_version`、`taxonomy_node`、`taxonomy_alias` | 草稿、激活、退役和版本固定已经具备 |
| 主副知识点关系 | `question_taxonomy_link.relation_type` | 能保存主副关系，但缺少“每维度最多一个主标签”约束 |
| 讲义修订 | `editor_document`、`editor_revision`、`editor_draft` | 内容不原地覆盖，适合建立搜索投影 |
| 讲义快照与导出 | 预览确认、不可变快照、导出请求和 renderer worker | 搜索可固定当前修订，导出继续固定快照 |
| 题篮与暂存 | 草稿版本、检查点、恢复、不可变快照 | 已具备版本和恢复模式 |
| 审计事件 | `audit_event` 和 Java 审计端口 | 模块发布、标签确认和模型建议接受应继续写入 |
| PostgreSQL 搜索基础 | `pg_trgm`、GIN 索引、题目搜索 API | 可以扩展，不需要立即增加外部搜索引擎 |
| 后台任务模式 | 导出 worker 的租约、重试和原子落盘 | 可借鉴到模块语义补全任务，但不能混用任务表 |

### 3.2 题目搜索现状

当前 `GET /api/v1/questions/search` 支持：

- 默认搜索审核通过修订，也可搜索待审核、未审核或已拒绝的当前修订。
- 按学科、学段、年级、题型和难度精确过滤。
- 在标题、课程、主知识点文字、材料、题干、答案和解析中做大小写不敏感包含搜索。
- 使用游标分页，并返回题目是否已被讲义或题篮引用。
- 数据库已经建立 `pg_trgm` 和全文检索索引。

当前限制：

- 查询按创建时间排序，不按文本相关性排序。
- 实现主要使用包含匹配，尚未使用 `similarity`、字段权重或命中高亮。
- 主知识点自由文本参与搜索，但标准化的 `question_taxonomy_link`，特别是副知识点和树形后代，
  尚未完整参与搜索和筛选。
- 中文短词、错字、同义词和别名没有统一的规范化策略。

结论：题目搜索可以支撑初期题篮选题，但不能直接视为三类内容资产的统一搜索方案。

### 3.3 知识结构现状

当前知识结构具备：

- 一个稳定的 `taxonomy_key` 可以拥有多个不可变版本。
- 一个工作区和知识体系键只能有一个激活版本。
- 节点保存编码、名称、父节点、排序和元数据。
- 别名经过规范化后保存。
- 题目知识点关联固定到题目修订和知识体系版本，后续激活新版不会篡改历史。

当前查询只支持：

- 指定工作区。
- 指定一个明确的激活版本。
- 使用完整知识点编码或完整规范化别名解析一个节点。

缺少名称模糊搜索、路径展示、父子范围过滤、命中方式、关联题目计数、废弃节点替代关系和
知识体系升级迁移任务。

### 3.4 标准化模块现状

当前仓库中没有正式的 `standard_module` 业务域。现有编辑器结构化 JSON 可以承载文字、公式、
思维导图和引用，但不能代替标准化模块，因为编辑器内容属于一份讲义修订，不具备跨讲义复用
所需的稳定身份、独立审核、独立版本、使用统计和生命周期。

因此以下能力目前均不存在：

- 单张图片、单个表格、单段文本或复合内容作为独立教学资产。
- 模块内容的不可变修订和生产修订指针。
- 模块引用精确版本，以及“被哪些讲义使用”的反向查询。
- 模块自己的主副知识点、适用范围和来源。
- 临时模块的个人可见、待整理、待审核和共享状态。
- 模块搜索投影和类型化结果预览。

这部分是本计划最大的新增业务域，而不是在现有表上简单增加一个搜索框。

### 3.5 讲义搜索现状

讲义目前拥有稳定文档身份、不可变修订、草稿指针、三种变体、预览确认、不可变快照和导出
任务。当前文档类型包括同步讲义与独立题包。

缺少：

- 按讲义标题、章节、正文、公式、思维导图节点和引用题目内容搜索。
- 将结构化编辑器 JSON 稳定展开为可搜索纯文本的投影器。
- 按章节或模块块切分长文档。
- 一份讲义多个章节命中后合并为一个结果卡片。
- 普通搜索只显示当前有效版本，管理搜索显式显示历史版本的接口合同。
- 讲义知识点和文件引用的完整关系投影。

### 3.6 权限、异步和可观测性现状

- `workspace_member` 已有角色，但请求仍直接接收 `actorUserId`；正式搜索必须从 Spring Security
  当前身份获得用户，不能相信客户端自报身份。
- 当前没有通用 outbox。既有审计文档明确要求只有出现真实异步消费者时才建立。模块语义补全
  将成为第一个明确需要持久任务、租约和重试的消费者，但 PostgreSQL 内部搜索投影仍可在业务
  事务中同步更新，不需要为了搜索提前增加消息中间件。
- 当前没有搜索查询、零结果、点击、选择和人工改写建议的质量数据。

## 5. 目标架构原则

### 5.1 业务真相与搜索投影分离

规范业务表是唯一真相。搜索投影只保存为检索和展示而展开的冗余数据，必须满足：

- 可由业务表全量重建。
- 不接受人工直接修改。
- 每条投影记录来源对象、精确修订和投影合同版本。
- 投影损坏不能反向污染业务内容。

### 5.2 多形态模块是一等资产，不是附件

标准化模块是“可独立复用、可版本化、可审核、可搜索的教学内容资产”。它可以是文本，也可以
是单张图片、一个结构化表格、一条公式、一棵思维导图或多个模块组成的复合模块。

普通文件成为标准化图片模块之前，至少要拥有模块身份、来源、名称、类型、适用范围和审核状态。
否则它仍然只是文件资产。

### 5.3 程序处理确定性，模型处理语义

程序负责哈希、文件类型、OCR 原文保存、表格结构、上下文继承、版本、权限和索引刷新。模型负责
标题建议、内容描述、教学用途、知识点候选、关键词和相似模块建议。

模型输出只进入建议区，不直接修改原始内容、正式标签、来源、版权或共享状态。

### 5.4 在线搜索不调用模型

搜索请求必须是低延迟、可重现和可降级的数据库查询。模型只在内容创建或后台补全时异步运行。
即使模型服务断网、EOF 或限流，用户仍能保存、检索自己的草稿并继续工作。

### 5.5 当前版本默认，历史版本显式进入

普通用户搜索默认只返回当前有效或审核通过版本，并按稳定对象 ID 去重。历史版本只能在管理或
审计模式中显式搜索。所有结果仍必须携带精确修订 ID，插入讲义后固定到该修订。

## 6. 标准化模块目标数据模型

### 6.1 稳定身份

建议新增 `standard_module`：

| 字段 | 用途 |
| --- | --- |
| `standard_module_id` | 跨版本稳定身份 |
| `workspace_id` | 租户边界 |
| `module_key` | 可选的稳定展示或集成键 |
| `module_type` | `rich_text/image/table/formula/mind_map/composite` |
| `title` | 当前展示名称，不承担历史内容真相 |
| `visibility` | 初期为 `private/workspace` |
| `status` | `draft/pending_review/active/archived` |
| `current_revision_id` | 当前工作修订 |
| `approved_revision_id` | 当前共享生产修订 |
| `owner_user_id` | 个人草稿和维护责任人 |
| 创建、更新字段 | 审计和排序 |

状态不应混入模型任务状态。模块可以是 `draft`，同时拥有一个 `failed_retryable` 的补全任务。

### 6.2 不可变修订

建议新增 `standard_module_revision`：

- `revision_no` 和内容哈希。
- `module_type` 和 `schema_version`。
- 类型化 `payload_json`。
- 结构化摘要和可选人工说明。
- 审核状态、创建人和创建时间。
- 来源证据与派生关系。

修订内容只新增不原地覆盖。标题、标签和来源的改变必须保留审计；影响内容语义的修改应创建新
修订。纯展示性拼写修正是否创建内容修订，可在合同阶段进一步细分为“内容修订”和“元数据修订”。

### 6.3 类型化内容合同

`payload_json` 不是任意 JSON。每种 `module_type + schema_version` 都必须有 Java 校验器、规范化器、
搜索文本提取器和前端合同。

#### 文本模块

保存结构化富文本源、纯文本投影和可引用资源，不把渲染后的 HTML 当作真相。

#### 图片模块

保存 `file_version_id`、图注、替代文本、OCR 结果引用和人工说明。图片二进制继续由文件资产域管理。
OCR 原文、人工修正和模型描述必须分开，不能互相覆盖。

#### 表格模块

保存表头、行、单元格、合并信息和说明等结构，不保存浏览器生成的 HTML 或仅保存截图。搜索文本
由表名、表头和单元格按稳定顺序提取。

#### 公式模块

保存 LaTeX、行内或块级显示方式、人工名称和语义说明。搜索可以使用公式名称、知识点和规范化
LaTeX；不能仅依赖符号相似度猜测公式用途。

#### 思维导图模块

保存稳定节点 ID、主题、层级、排序和挖空标记。搜索使用中心主题、节点文字和树路径。

#### 复合模块

保存有序的子模块修订引用，不复制子模块内容。必须防止循环引用，并明确子模块升级不会自动改变
已经固定的复合模块修订。

### 6.4 关系表

建议新增：

- `standard_module_asset_reference`：固定文件版本及用途。
- `standard_module_taxonomy_link`：固定知识体系版本与节点，保存主副关系和来源。
- `standard_module_child_reference`：复合模块的有序子模块修订。
- `editor_module_reference`：讲义修订引用的模块修订及落位信息。
- `standard_module_source_link`：原文件、页码、区域或派生模块来源。

“使用次数”不作为手工维护字段，应通过引用关系投影或汇总得出。

## 7. 临时内容与维护生命周期

### 7.1 推荐流程

```text
捕获或上传
  -> 个人草稿立即保存
  -> 程序确定性提取
  -> 模型异步补全建议
  -> 用户逐项确认或修改
  -> 提交审核
  -> 工作区共享
  -> 归档但保留历史引用
```

### 7.2 创建时自动获得的信息

- 类型、哈希、创建者、工作区和时间。
- 文件名、图注、表头、公式源码或首段文字。
- 从当前讲义继承的学科、学段、年级和知识点上下文。
- 从用户教学范围得到的默认学科和学段；这只是默认值，不是无确认的事实。
- 图片 OCR、表格文本展开和内容摘要候选。
- 来源文件、页面、区域或父模块。

### 7.3 分阶段必填规则

| 阶段 | 必填或必须可得 |
| --- | --- |
| 保存个人草稿 | 模块类型、内容或文件版本、创建者、来源上下文 |
| 方便个人检索 | 临时标题或可提取文本；允许显示“待整理” |
| 提交审核 | 正式名称、学科、学段、至少一个主知识点、来源状态 |
| 工作区共享 | 审核通过修订、权限、版权或可用范围、完整最小标签集 |
| 正式讲义发布 | 所有引用固定到明确修订，缺失引用或未授权资产失败关闭 |

副知识点、详细摘要和扩展教学用途不应在首次保存时全部强制，否则用户会绕开模块系统。共享前的
最低质量门禁则不能取消。

### 7.4 谁负责维护

- 创建者负责个人草稿和模型建议确认。
- 审核者负责共享前的教学语义与来源确认。
- 管理员负责批量归类、知识树迁移、重复内容治理和长期未维护内容。
- 系统负责提取、索引、失败重试、缺失字段提示和一致性检查。

需要提供“待整理模块”队列，至少可筛选：无主知识点、临时名称、OCR 低置信度、来源未知、模型
补全失败、长期未审核、疑似重复和引用旧知识体系的模块。

## 8. 模型语义补全设计

### 8.1 持久任务

建议新增 `module_enrichment_job`，状态使用：

```text
queued / running / succeeded / failed_retryable / failed_final / cancelled
```

任务保存模块修订、加工配置版本、幂等键、尝试次数、租约持有者、租约到期时间、结构化错误和
输入哈希。幂等键至少包含 `module_revision_id + enrichment_profile_version`。

后台 worker 使用 PostgreSQL 行锁或 `SKIP LOCKED` 领取任务，写心跳或短租约，超时后可回收。
模型调用失败不能回滚已经成功保存的模块草稿。

### 8.2 字段级建议

建议新增 `module_enrichment_suggestion`：

- 建议字段、建议值、置信度和证据。
- 模型、模型版本、加工配置和提示合同版本。
- `pending/accepted/edited/rejected/expired` 状态。
- 确认用户、确认时间和最终采用值。

模型适合建议：标题、说明、模块类型、学科、学段、年级、教学用途、关键词、别名、知识点候选和
相似模块。模型不得修改图片、表格单元格、公式、原始正文、来源或版权结论。

### 8.3 知识点推荐必须受约束

模型不能自由生成一个知识点名称后直接入库。推荐流程应为：

1. 程序依据学科、学段、名称、别名和内容从明确的激活知识体系版本检索候选节点。
2. 模型只在候选节点中排序或选择，并返回节点 ID、置信度和依据。
3. Java 服务校验节点仍属于指定版本且状态可用。
4. 用户确认后才写入正式主副知识点关系。

### 8.4 搜索使用边界

- 未确认模型建议可以帮助创建者在个人草稿中定位，但必须带“模型建议”标记。
- 未确认建议不进入工作区共享搜索的正式字段和筛选项。
- 用户接受建议后，业务事务写入正式字段并刷新搜索投影。
- 在线搜索不调用模型，也不因模型不可用而失败。

## 9. 搜索基础设施设计

### 9.1 模块边界

新增独立 `search` Spring Modulith 模块，公开稳定的 `SearchGateway`，业务模块只发布可投影的规范
数据，不依赖具体 SQL、PostgreSQL 扩展或未来 OpenSearch SDK。

第一阶段搜索实现仍在 PostgreSQL 中。由于业务表和搜索投影位于同一数据库，创建、确认、激活和
归档时可在同一事务中更新投影，获得强一致性。外部搜索引擎尚未存在，因此此时不增加 outbox。

同时提供全量重建命令和一致性核验命令。投影可重建是验收条件，不是运维补丁。

### 9.2 通用搜索投影

建议使用派生的 `search_document` 和 `search_chunk`，而不是让所有业务对象共用一张规范内容表。

`search_document` 保存：

- 工作区、对象类型、稳定对象 ID、精确修订 ID和逻辑版本。
- 标题、副标题、别名、知识路径和规范化搜索文本。
- 学科、学段、年级、状态、可见性、所有者等高频筛选列。
- 当前版本标记、审核状态、内容哈希、投影合同版本和更新时间。
- 结果卡片所需的少量类型化展示元数据。

`search_chunk` 保存：

- 父搜索文档、稳定块 ID、块类型、标题、正文、顺序和内容哈希。
- 讲义章节、表格局部或复合模块子区块的可搜索文本。
- 与父文档相同的权限和当前版本边界，防止命中块泄漏父文档。

需要单独的搜索知识点关系投影，以支持主知识点、副知识点、父节点及后代过滤。高频筛选字段必须
是类型化列或关系表，不能全部塞进不可索引的任意 JSON。

### 9.3 文本规范化

所有对象共享最小规范化：

- Unicode 兼容规范化、全角半角统一、大小写统一和首尾空白处理。
- 标点、连续空白和常见公式外围符号的稳定处理。
- 保留原始展示文本，规范化文本只用于匹配。
- 知识点别名和业务同义词由受控表维护，不在查询时让模型临时扩写。
- 中文两字短词使用精确、前缀和包含优先；三字组索引对过短查询可能退化，必须有限制和压测。

## 10. 三类对象的搜索策略

### 10.1 知识点搜索

搜索字段：编码、正式名称、别名、完整祖先路径、可选说明。过滤字段：知识体系版本、学科、学段、
状态和父节点范围。

推荐固定排序：

```text
编码完全一致
> 正式名称完全一致
> 别名完全一致
> 正式名称前缀
> 正式名称包含
> 路径或祖先命中
> pg_trgm 字符近似
```

返回值至少包括节点 ID、版本 ID、编码、名称、完整路径、命中字段、命中类型、关联题目和模块数量、
状态及替代节点提示。

知识点选择器默认只搜索激活版本。管理界面可以显式搜索草稿和退役版本。知识点选择不使用纯向量
结果，避免把语义相关但结构上不同的节点误当作正式标签。

### 10.2 标准化模块搜索

所有模块共享名称、别名、知识点、适用范围、来源、类型和说明；不同类型增加不同搜索文本：

| 类型 | 补充搜索内容 | 结果预览 |
| --- | --- | --- |
| 文本 | 正文、摘要、小标题 | 命中摘要 |
| 图片 | 图注、人工替代文本、OCR、模型描述 | 缩略图和命中来源 |
| 表格 | 表名、表头、单元格、说明 | 表头和命中行 |
| 公式 | 公式名称、LaTeX、语义说明 | 渲染公式 |
| 思维导图 | 中心主题、节点文字、路径 | 局部树或中心主题 |
| 复合模块 | 自身名称和子模块摘要 | 子模块命中列表 |

推荐排序：名称精确、知识点精确、别名前缀、标题包含、类型化正文命中、受控业务质量信号。使用次数
和最近使用只能作为文本相关性相同后的并列项，不能让热门但不相关的模块压过精确命中。

个人搜索包括自己的草稿和待整理模块；工作区普通搜索只包括共享审核通过修订；管理搜索可查看
待审核、归档和历史版本。

### 10.3 讲义搜索

讲义投影器从结构化编辑器修订中提取：

- 讲义标题、变体、章节标题和正文。
- 公式的 LaTeX 与人工说明。
- 思维导图中心主题和节点文字。
- 表格标题、表头和单元格文字。
- 固定题目修订的可展示题干和知识点。
- 固定标准化模块修订的标题与类型化摘要。

切块应遵循章节、模块块和题目块边界，不按固定字符数粗暴切断。每个块携带文档、修订、章节、
顺序、学科、学段、权限和状态。

搜索命中多个章节时，按稳定讲义 ID 合并为一张卡片，展示最相关的一个或两个片段。普通搜索只
显示当前有效修订；历史审计模式显式显示修订号和时间，不与当前讲义混排。

## 11. 统一搜索 API 合同

建议保留专业入口：

```text
GET /api/v1/taxonomy-versions/{taxonomyVersionId}/nodes/search
GET /api/v1/standard-modules/search
GET /api/v1/handouts/search
```

同时提供顶部全局搜索：

```text
GET /api/v1/search
  ?query=二次函数
  &types=knowledge_point,standard_module,handout
  &subject=数学
  &stage=初中
  &cursor=...
```

通用结果包含：

- `objectType`、稳定对象 ID 和精确修订 ID。
- 标题、副标题、类型化预览和完整路径。
- 命中字段、命中片段和高亮范围。
- 学科、学段、状态、版本和是否已引用。
- 不透明游标；游标必须包含排序分数边界和稳定 ID，保证翻页确定性。

原始数据库相关性分数不作为长期前端合同。前端可以使用 `matchKind` 或相关性档位展示，但不依赖
某个搜索引擎的浮点分数。

## 12. 版本与知识结构升级

### 12.1 搜索版本规则

- 搜索文档绑定精确业务修订。
- 当前审核通过指针改变时，原子切换默认可见投影。
- 历史投影可以保留或按需重建，但普通搜索必须去重。
- 讲义插入题目或模块后固定修订，后续搜索结果变化不能改变旧讲义。

### 12.2 知识节点迁移

知识体系新版需要新增显式节点演化关系，至少表达：

```text
unchanged / renamed / merged_into / split_into / retired_without_replacement
```

激活新版不会自动重写旧题目和旧模块标签。系统生成迁移任务，列出受影响题目、模块和讲义，由
管理员批量确认。迁移结果创建新修订或新标签关系，不篡改历史。

### 12.3 主副标签待决策

当前数据库允许保存 `primary` 和 `secondary`，但没有保证同一对象、同一知识体系维度最多一个主
标签。实施前必须确定：

- 副标签升级为主标签时，旧主标签是降级、移除还是要求用户选择。
- 草稿能否没有主标签；本计划建议允许。
- 提交审核和共享时是否强制一个主标签；本计划建议强制。
- 模型建议能否自动改变主副关系；本计划建议不能。

该规则确定后，必须同时写入应用事务、数据库唯一约束、并发测试和审计事件。

## 13. 权限与安全

生产搜索上线前必须完成正式身份接入：

- Keycloak 或其他 OIDC 身份提供方负责账号、密码和登录。
- Spring Security 从已验证身份生成当前用户，不再接收客户端自报 `actorUserId`。
- TeachBase 继续负责工作区角色、教学范围和内容权限。

第一阶段模块可见性建议只提供 `private` 与 `workspace`，避免一开始建设复杂 ACL。接口和投影中保留
稳定权限端口，未来可增加按用户或用户组授权。

每次搜索在数据库层同时施加工作区、成员状态、对象可见性、生命周期和审核状态过滤。不得先搜索
全部内容再在 Java 内存中剔除无权结果，因为这会导致计数、分页、摘要和日志泄漏。

OCR 和模型输入可能包含未发布题目与内部讲义。模型供应商、日志脱敏、保留期限和业务密钥需要由
部署配置管理；搜索索引不得保存业务密钥或模型请求原文日志。

## 14. 首批数据与历史内容进入方式

首批数据使用现有 Loader 的模式扩展，而不是人工直接写业务表：

```text
validate -> dry-run -> import -> verify
```

建议分三批：

1. 导入并激活受控知识体系版本、节点和别名。
2. 导入标准化模块，确定性提取内容，无法匹配的知识点进入待归类队列。
3. 为现有讲义当前修订回填搜索投影，不改变讲义内容和历史快照。

导入清单记录输入包版本、哈希、知识体系版本、成功数、复用数、失败数和待人工处理数。高置信度
模型建议也只能进入待确认，不绕过审核。

## 15. 分阶段实施计划

### 阶段 0：业务合同冻结

交付：模块类型清单、生命周期、最小元数据、主副标签规则、可见性、版本语义和 API 草案。

退出条件：所有 P0 业务歧义有书面决定；准备真实知识点、图片、表格和讲义样本作为测试材料。

### 阶段 1：知识点模糊搜索

交付：名称、编码、别名、路径和字符相似搜索；学科、学段、版本和父节点筛选；确定性排序、分页、
结果计数和真实 PostgreSQL 门禁。

退出条件：黄金查询集中精确编码和正式名称 Top 1；常用别名稳定命中；退役或错误版本不混入默认结果。

### 阶段 2：标准化模块核心业务域

交付：身份、不可变修订、六种类型合同、文件引用、知识点关系、复合引用、审核、个人/工作区可见性、
讲义引用和审计。

退出条件：单张图片、结构化表格、文本、公式、思维导图和复合模块均可创建、修订、审核、引用，
历史讲义引用不随模块新版变化。

### 阶段 3：临时捕获与模型补全

交付：确定性提取器、补全任务、租约、重试、字段级建议、人工接受/修改/拒绝、失败恢复和待整理队列。

退出条件：断网或模型 EOF 不影响草稿保存；任务可恢复；模型不能越过候选知识体系或自动发布。

### 阶段 4：标准化模块搜索

交付：类型化搜索投影、个人草稿搜索、工作区共享搜索、类型筛选、知识点筛选、预览、高亮和版本去重。

退出条件：临时模块保存后可由创建者找到；未确认建议不会污染共享结果；图片和表格显示正确预览。

### 阶段 5：讲义章节搜索

交付：编辑器 JSON 投影器、稳定章节切块、引用内容展开、当前版本搜索、历史模式、结果分组和权限过滤。

退出条件：一份讲义多块命中只返回一张卡片；快照与当前修订不串版；无权用户不能获得标题或摘要。

### 阶段 6：统一搜索与质量治理

交付：统一 `SearchGateway`、全局 API、对象分组、分面计数、搜索行为事件、零结果队列、全量重建和
一致性核验。

退出条件：三类对象可统一搜索，专业选择器仍保持专用排序；投影删除后可从业务表完整重建。

### 阶段 7：容量复核与可选升级

依据真实数据量、P95 延迟、零结果率和黄金查询质量决定是否接入 OpenSearch。没有证据时继续使用
PostgreSQL；不得仅因“以后可能很大”提前增加双写、集群和索引运维。

## 16. 测试与验收门禁

### 16.1 数据与版本

- 每种模块类型的合同校验、规范化、哈希和修订测试。
- 并发修改不能覆盖他人新修订。
- 复合模块禁止循环引用。
- 当前修订、审核通过修订和历史修订不串版。
- 模块或知识树升级不能改变既有讲义快照。

### 16.2 搜索正确性

- 中文精确、前缀、包含、别名和字符近似样本。
- 英文大小写、短语、公式和混合中英文样本。
- 主副知识点、父节点后代和版本过滤。
- 图片 OCR、表格单元格、公式、思维导图节点和讲义章节命中。
- 一个稳定对象多版本和多章节结果去重。
- 高亮范围必须对应返回展示文本，不能用规范化文本位置直接渲染。

### 16.3 权限与状态

- 私有草稿只对创建者和授权管理人员可见。
- 未审核模块不进入普通工作区搜索。
- 暂停或移除成员不能继续搜索工作区内容。
- 无权内容不出现在结果、计数、摘要、建议或搜索日志中。

### 16.4 模型与任务韧性

- 超时、EOF、限流、无效 JSON 和非法知识点 ID。
- worker 中断后租约回收和幂等重试。
- 相同修订与加工配置不重复计费。
- 用户拒绝建议后不会被同一建议重复覆盖。
- 模型失败时确定性搜索仍可用。

### 16.5 搜索质量黄金集

在开发前从真实教师工作流建立查询集，至少覆盖：

- 30 个知识点短查询与别名。
- 30 个模块名称、用途和内容查询。
- 20 个讲义标题与章节内容查询。
- 20 个应当无结果或只返回受限结果的查询。

每条记录预期 Top 1、Top 3 或 Top 5 对象，以及不能出现的对象。排名规则变更必须跑黄金集，不接受
仅凭单个演示样本调整权重。

### 16.6 初期性能目标

以下是验收目标，不是未经压测的承诺：

- 约一万知识节点下，知识点联想查询本地 PostgreSQL P95 不高于 150 ms。
- 约十万搜索文档及合理章节块下，统一搜索 P95 不高于 300 ms。
- 分页不使用深 offset，始终使用确定性游标。
- 同一数据库内业务写入成功后，规范搜索投影立即一致；模型建议按异步任务状态显示。
- 全量重建可中断、可续跑、可核验数量和哈希。

## 17. 可观测性与质量反馈

建议记录不含敏感正文的搜索行为事件：

- 查询规范化哈希、对象类型、筛选条件和耗时。
- 结果数量、是否零结果、选择对象和结果位置。
- 用户是否改写查询或切换筛选。
- 模型建议接受、编辑和拒绝比例。

这些数据用于发现缺失别名、错误排序和常见无结果，不用于悄悄改变知识结构。任何业务排名调整都应
有版本和黄金集对比。

监控至少包括：搜索 P50/P95/P99、慢查询、零结果率、投影积压、补全任务失败率、租约回收数、
索引一致性差异和全量重建状态。

## 18. 主要风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| 用户临时保存时被迫填太多字段 | 个人草稿最小保存，发布前再强制完整元数据 |
| 临时内容长期无人整理 | 待整理队列、责任人、批量维护和过期提示 |
| OCR 错误污染搜索 | OCR 标明来源，只作辅助字段，不覆盖人工内容 |
| 模型幻觉知识点或来源 | 候选集约束、字段级建议、人工确认、来源禁止推断为事实 |
| 通用 JSON 演变为不可维护大杂烩 | 按模块类型和 schemaVersion 提供严格 Java 合同与迁移器 |
| 多版本搜索重复和串版 | 稳定对象 ID 去重、默认当前修订、结果固定 revisionId |
| 权限过滤晚于搜索导致泄漏 | 在数据库查询阶段施加工作区、身份、可见性和状态条件 |
| 搜索投影与业务表漂移 | 同事务更新、内容哈希、重建命令和一致性门禁 |
| 中文短词误命中过多 | 精确/别名/前缀优先，限制近似阈值，用黄金集调参 |
| 提前引入 OpenSearch 增加维护负担 | PostgreSQL 先行，以容量和质量证据触发升级 |
| 主副标签规则不明确造成数据损坏 | 实施前冻结语义，并同时落实事务、唯一约束和审计 |

## 19. 工作量评估

以下为聚焦后端和数据库的常规工程量，不包含完整前端页面、模型提示调优、海量人工标注和
OpenSearch 生产部署：

| 工作包 | 估算 |
| --- | --- |
| 合同冻结与测试样本 | 1-2 个工程日 |
| 知识点模糊搜索 | 2-4 个工程日 |
| 标准化模块核心域 | 5-8 个工程日 |
| 临时捕获与模型补全 | 4-7 个工程日 |
| 标准化模块搜索 | 2-4 个工程日 |
| 讲义章节搜索 | 3-5 个工程日 |
| 统一搜索、质量和全量重建 | 3-5 个工程日 |

总量约为 20-35 个聚焦工程日，适合拆成六至七个可独立验收的里程碑。知识点与讲义基础搜索可以
较早交付；标准化模块和模型补全是主要工作量。直接一次性建设外部搜索集群不会减少业务建模工作，
只会提前增加双写、一致性和运维成本。

## 20. 实施前必须研究并确认的决策

1. 副标签升级为主标签时，旧主标签降级、删除还是弹出选择。
2. 题目和标准化模块共享前的最小标签集是否完全相同。
3. 哪些角色可以发布模块、审核模块和查看他人的个人草稿。
4. 用户从讲义中截取模块时，默认继承哪些学科、学段、年级和知识点。
5. 图片来源和版权状态的允许值及谁负责确认。
6. 表格整体作为一个模块，还是允许单行、单元格成为独立可引用对象；初期建议只把整表作为模块。
7. 复合模块子项升级时是否提供显式“升级引用”工具；建议不自动升级。
8. 模型建议达到何种置信度可以批量确认，但无论置信度多高都不自动发布。
9. 知识体系节点合并和拆分时，谁拥有最终迁移决定权。
10. 历史版本是否参与普通关键词搜索；本计划建议默认不参与。

## 21. 明确不在首期实施的范围

- 不用模型实时回答每一次搜索请求。
- 不把向量搜索作为知识点正式选择依据。
- 不引入 Elasticsearch/OpenSearch、Redis 或 Kafka。
- 不把图片二进制、渲染 HTML、SVG 或截图作为规范模块内容。
- 不自动重写历史题目、模块、讲义或知识点关系。
- 不在没有真实规则前实现难度体系。
- 不把四条题目生产链迁入 Java，也不修改其提示词和模型机制。
- 不一次性建设复杂组织级 ACL；首期以个人与工作区可见性为主。

## 22. 完成定义

本计划全部完成时，应能够证明：

1. 教师可以临时保存文本、图片、表格、公式、思维导图和复合模块，并立即在个人范围找到。
2. 程序与模型可以异步补全信息，失败不影响保存，建议未经确认不会污染共享库。
3. 共享模块拥有正式名称、学科、学段、主知识点、来源、审核和不可变修订。
4. 知识点、模块和讲义可以分别按适合自身的规则模糊搜索，也可以通过统一入口聚合。
5. 搜索结果遵守工作区、身份、状态、审核和版本边界，不泄漏无权内容。
6. 图片、表格和讲义章节返回类型化预览，不退化成难以理解的长文本片段。
7. 题目或模块升级不会改变既有讲义快照；搜索结果始终携带精确修订。
8. 搜索投影可以从业务表全量重建并通过数量、哈希和黄金查询核验。
9. 主副标签、知识树迁移和发布门禁有明确事务规则、数据库约束和审计记录。
10. 在达到外部搜索引擎迁移条件之前，PostgreSQL 能通过规定数据量和性能门禁。

## 23. 市场与技术依据

- PostgreSQL `pg_trgm` 提供字符相似度、`LIKE/ILIKE` 索引和 GiST/GIN 支持，但过短查询可能无法
  提取有效三字组，需要单独策略：<https://www.postgresql.org/docs/17/pgtrgm.html>
- PostgreSQL 全文检索支持字段权重、`ts_rank` 和结构化相关性：
  <https://www.postgresql.org/docs/current/functions-textsearch.html>
- Elastic 推荐多字段查询并通过字段 boost 区分标题、描述和标签的重要性：
  <https://www.elastic.co/guide/en/elasticsearch/reference/current/full-text-filter-tutorial.html>
- Elastic Smart Chinese 插件说明了中文分词需要专门分析器，而不是直接沿用英文规则：
  <https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-smartcn>
- Algolia 将字段优先级、分面、层级分类和版本去重作为成熟搜索的重要组成：
  <https://www.algolia.com/doc/guides/managing-results/must-do/searchable-attributes/how-to/configuring-searchable-attributes-the-right-way>
  <https://www.algolia.com/doc/guides/managing-results/refine-results/faceting>
  <https://www.algolia.com/doc/guides/managing-results/refine-results/grouping/>
- Algolia 明确指出常规拼写距离容错不适用于中文和日文，因此中文仍需别名、规范化、包含和业务
  词表：<https://www.algolia.com/doc/guides/managing-results/optimize-search-results/handling-natural-languages-nlp>
- Azure 文档检索采用父文档与子块投影，并要求每个内容块继承权限元数据：
  <https://learn.microsoft.com/en-us/azure/search/search-how-to-define-index-projections>
  <https://learn.microsoft.com/en-us/azure/search/search-indexer-sharepoint-access-control-lists>
- OpenSearch 将关键词和语义检索组合为混合搜索；该能力适合作为后续升级，而不是替代当前精确
  标签和结构化筛选：<https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/index/>

## 24. 建议结论

建议批准总体方向，但暂不直接进入全部实现。先完成阶段 0 的业务合同冻结，并优先交付知识点模糊
搜索，以真实教师查询建立黄金集。随后建设标准化模块核心域，再接入模型补全、模块搜索和讲义搜索。

这条顺序能够避免两个极端：一是先建一个只能保存文本的临时模块表，导致图片和表格很快返工；
二是先上重型搜索和向量系统，却没有稳定的资产身份、版本、权限和审核数据可供索引。

最终目标不是“让所有内容都能被某个搜索框碰巧搜到”，而是建立一个可持续维护的教学资产系统：
临时内容不会丢，正式内容有标准，历史引用不漂移，模型只辅助判断，用户能快速找到并安全复用。
