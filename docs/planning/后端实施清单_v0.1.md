# 后端实施清单 v0.1

这份清单不是再讲一遍架构理念，而是把 [后端处理结构设计_v0.3.md](/C:/Users/EDY/Documents/教研基建/后端处理结构设计_v0.3.md:1) 落成真正可执行的实施顺序。

- 开工前拆任务

## 2. 完成定义

这轮“做完”的标准，不是文档写漂亮，而是至少做到下面三点同时成立：

1. 结构已经落到可审的数据库草案与模块边界
2. 当前状态已经单独汇报，不再把设计和实现混在一起
3. 下一步实施顺序、验收口径和风险项已经明确

## 3. 当前阶段目标

当前阶段不追求“一次性做完整平台”，而是先把后端从：

- `demo / 文件产物 / mock API`

提升到：

- `有事实源 / 可重跑 / 可审核 / 可追溯 / 可扩 worker`

## 4. P0 实施包

### 4.1 P0-1：修订模型

目标：

- 让 `lesson / source_node / task` 不再是可直接覆盖的单份数据

必须落地：

- `lesson_revision`
- `source_node_revision`
- `task_revision`
- `active_revision_id`
- `published_revision_id`

完成标志：

- 重跑时生成新 revision，而不是覆盖旧结果
- 老审核记录仍能定位到原 revision
- 发布结果和工作中结果能区分

### 4.2 P0-2：任务事实源

目标：

- 把任务系统从“脚本串起来”变成“数据库可追踪”

必须落地：

- `run`
- `job`
- `job_dependency`
- `outbox_event`

完成标志：

- 所有导入、重跑、导出都有 `run_id`
- 每个执行单元都有 `job_id`
- 多依赖关系可以落库
- Redis 不再是唯一事实源

### 4.3 P0-3：artifact 血缘

目标：

- 让任意导出物都能回溯上游

必须落地：

- `artifact`
- `artifact_dependency`
- `lifecycle_status`

完成标志：

- 能回答某个导出由哪版 OCR、哪版结构树、哪版插件生成
- 上游重跑后，下游旧 artifact 会变 `stale`

### 4.4 P0-4：视觉组件主对象

目标：

- 把“页图 / OCR / 裁片 / 组件”从临时文件提升为稳定主对象

必须落地：

- `page_asset`
- `component`
- `component_link`

完成标志：

- 题目和结构节点能引用稳定 `component_id`
- 局部重组不再只靠文件路径

### 4.5 P0-5：审核发布主流程

目标：

- 把审核从“人工看一眼”变成正式状态机

必须落地：

- `review_task`
- 发布快照
- 回滚语义

完成标志：

- `job` 成功只表示已生成可审核 artifact
- `review_task` 独立推进审核状态
- 审核通过后才进入 published 结果

## 7. 建议实施顺序

最推荐的顺序是：

1. 先建表，不先堆接口
2. 先把 `run/job/artifact/revision` 跑通，再谈完整工作台
3. 先让现有导出和导入脚本接入 job 骨架，再逐步替换
4. 先让重跑安全，再做高并发

## 9. 每阶段验收口径

### 9.1 P0 阶段验收

必须同时通过：

- 同一个 job 重复投递两次，只产生一份有效结果
- worker 中断后，能从最近 artifact 继续
- 局部重跑不会覆盖老师已审核修改
- 导出物能回溯到上游 artifact 链

### 9.2 P1 阶段验收

必须同时通过：

- 同一组文档可以管理学生版、教师版、答案册等多成员关系
- 质量失败能看到具体规则项和证据
- 夜间批处理不会要求另一套业务代码

### 9.3 P2 阶段验收

必须同时通过：

- 发布新考点版本不破坏旧讲义已发布结果
- 学科插件扩展不会破坏核心数据一致性

## 10. 当前阶段不该做的事

为了避免投入分散，当前不建议优先做：

- 全量微服务拆分
- 分布式数据库
- 提前优化所有学科的专表
- 先做复杂前端而不补后端事实源
