# 开发工作流与技术栈资源说明 v0.1

## 1. 整体工作方式

当前项目采用“样例驱动、视觉优先、人工可校核、逐步产品化”的开发方式推进。

它不是先完整设计一套大平台再开发，而是先用真实讲义和题目样例验证关键链路，再把已经验证过的能力逐步沉淀成稳定模块。这样做的原因是：讲义版式、题目结构、学科差异和视觉识别质量都会直接影响结果，必须边验证边收敛。

目前主线可以概括为：

```text
真实样例资料
→ 视觉拆解与组件识别
→ 讲义结构与题目关系整理
→ 模型辅助识别与人工校核
→ 工作台验证
→ 导出与演示交付
→ 后端运行骨架沉淀
```

## 2. 开发工作流

### 2.1 样例与需求收敛

先选择典型讲义和题目材料做样例，不直接从全量资料开始。

当前样例覆盖了标准讲义、教师版/学生版资料、老师补充题目，以及部分英语、数学等不同版式。通过样例先确认三件事：

- 资料能否被拆成稳定结构
- 题目和非题组件能否分开管理
- 老师是否能通过审核页面看清楚问题并修正

### 2.2 视觉拆解与组件沉淀

讲义处理不是纯文本处理，当前坚持“原图是真值，文字是辅助”。

处理时会先把 PDF 或资料页转成页面图，再识别页面里的栏目、题块、图示、答案解析、知识梳理等组件。题目文字如果识别不稳定，不会直接当作正文使用，而是降级为 OCR 参考，保留原图给人工复核。

这一层已经形成了多版脚本和样例结果，包括页面拆解、组件切分、题块截图、质量检查、人工审核预览等能力。

### 2.3 结构编排与题目治理

拆出来的内容不会直接变成散题，而是挂回讲义结构。

当前核心结构是：

- `source_tree`：讲义结构树，作为题目主归属
- `component`：页面组件，承接视觉切分结果和后续重组
- `task`：题目实体，承接题干、题图、答案解析、风险信息
- `checkpoint`：考点映射层，用来表达教研判断，不替代讲义主结构

这样设计的目的是：讲义结构、题目、组件和考点判断可以分开管理，后续多学科扩展时不需要把所有字段都塞进同一张大表。

### 2.4 模型辅助与人工校核

模型主要用于视觉理解、题目转录、结构判断和考点候选，不直接替代最终审核。

当前已经验证过火山 Ark / Doubao 相关调用链路，也保留了原始响应和 token 信息。初期视觉模型拟采用 Doubao 1.8V，其他结构模型、考点模型和运行模型继续保持评测状态。

人工校核是当前 1.0 阶段的必要环节，重点看：

- 题块是否切完整
- 跨页题是否接完整
- 文字转录是否可靠
- 题目是否挂到正确讲义结构下
- 考点映射是否需要人工调整
- 是否存在奇怪组件组合或无效内容

### 2.5 工作台验证

当前工作台是本地演示与验证形态，主要用于把拆解结果变成可看、可点、可审核的界面。

已经形成的能力包括：

- 课次与讲义样例浏览
- 题块列表与原图预览
- OCR 参考与可信文字分层展示
- 风险标签与审核队列
- 讲义结构和题块关系查看
- 导出记录和样例回放

这部分目前仍是 demo / mock workbench 形态，上传、真实队列、状态回写、多人权限等能力还需要继续产品化。

### 2.6 导出与交付验证

当前导出链路已经可以生成 DOCX、PDF、PPTX 等演示产物，并能形成外发演示包。

但当前导出更偏“结构化结果打包”，还不是最终形态的“保留原讲义骨架再替换题目”。后续正式导出需要继续补：

- 非题结构保真
- 讲义栏目和知识点顺序保留
- 题组标签不被打散
- 组件库或版式资产库
- 批量导出任务队列、超时和取消机制

### 2.7 后端运行骨架沉淀

后端方向已经从“脚本串联”开始往“可追踪运行骨架”演进。

当前已落出一版本地文件持久化的 runtime backbone，用来验证：

- `run`
- `job`
- `artifact`
- `lesson_revision`
- `source_node_revision`
- `task_revision`
- `review_task`
- `artifact lineage`

这套骨架已经接入现有导出 API，可以把导出登记成 run/job/artifact，并查询产物血缘。下一步需要从文件状态迁移到正式数据库和队列。

## 3. 开发协作工具与产出方式

### 3.1 Codex 开发协作

当前开发过程中使用 Codex 作为主要的 AI 开发协作工具。

它的作用不是替代项目判断，而是把个人开发过程里的“方案拆解、代码落地、文档整理、联调验证、材料产出”串起来，降低单人推进时的切换成本。

在本项目中，Codex 主要承担以下工作：

- 结合现有代码仓、历史讨论和样例结果，协助梳理系统结构、数据关系和阶段目标
- 编写和调整 Python / Node.js / HTML / CSS / JavaScript 等本地代码
- 生成和维护拆题脚本、工作台 demo、导出脚本、后端运行骨架等工程文件
- 整理 BRD、技术说明、架构图说明、流程说明和对外汇报口径
- 根据运行结果继续修正方案，例如把 OCR 定位为参考层、把原图作为真值、把任务处理沉淀成 run/job/artifact
- 协助检查当前实现和目标方案之间的差距，避免 demo 能跑但后续难以产品化

因此，当前开发方式可以理解为：

```text
业务判断与样例选择由项目负责人把控
→ Codex 协助拆解方案和生成实现
→ 本地环境运行验证
→ 根据样例和审核结果继续调整
→ 将稳定部分沉淀为文档、脚本、工作台和后端骨架
```

这个工具链适合当前阶段快速试错和形成可演示成果。正式上线后，Codex 不属于系统运行依赖，生产系统仍然需要依靠数据库、队列、权限、日志、模型服务和部署环境来稳定运行。

### 3.2 其他开发与协作工具

- Figma：用于绘制整体架构图、流程图和领导可理解的结构示意图
- 本地编辑与终端环境：用于代码修改、脚本运行、服务启动和结果检查
- Office / 文档工具链：用于生成 DOCX、PDF、PPTX 等交付材料
- 浏览器工作台：用于验证老师审核、题块浏览、风险查看和导出记录等交互

## 4. 当前技术栈

### 4.1 本地开发与处理链路

- Python：用于 PDF 渲染、视觉拆解、题块处理、DOCX/PDF/PPTX 生成
- Node.js：用于本地 API、工作台数据构建、演示包打包、runtime 骨架服务
- PowerShell：用于 Windows 本地一键启动、停止服务和演示环境管理
- HTML / CSS / JavaScript：用于本地工作台和领导演示页面

### 4.2 视觉与文档处理

- PyMuPDF / fitz：PDF 页面读取与渲染
- Pillow / NumPy：页面图、题块截图、视觉标注和图像处理
- OpenPyXL：人工审核表、结构化检查表输出
- python-docx：DOCX 文档生成与编辑
- ReportLab：PDF 生成
- python-pptx：PPTX 汇报或罗盘类材料生成

### 4.3 模型与 AI 能力

- Doubao 1.8V：初期视觉识别与页面理解候选模型
- 火山 Ark / Doubao：已用于题目落位和视觉辅助判断试验
- 后续模型：结构模型、考点模型、转录模型继续评测后确定

模型使用原则是：先跑稳流程，再比较模型效果；模型输出必须保留原图、证据和人工复核入口。

### 4.4 工作台与服务

- 本地静态服务：当前工作台通过 `8787` 端口演示
- Node API 服务：当前导出与 runtime API 通过 `8790` 端口演示
- mock workbench：承接讲义浏览、题块审核、导出记录、演示数据
- runtime backbone：承接 run/job/artifact/revision/review 的本地验证

### 4.5 数据与运行支撑

当前阶段：

- 文件状态存储
- 本地 JSON / JS 数据包
- 本地导出目录
- 本地演示服务

正式化方向：

- Postgres：作为任务、结构、审核和产物的事实源
- Redis 或 Postgres 队列：承接异步任务投递
- 对象存储：保存原始文件、页面图、题块截图、导出产物
- Cloudflare Access / Tunnel：作为初期访问安全和外部入口方案

## 5. 资源说明

### 5.1 当前开发环境

当前个人开发环境按 `4核 / 8G` 估算。

这档资源可以支撑：

- 单人开发
- 本地 demo 演示
- 小批量样例验证
- 5 人以内的轻量测试
- 串行或低并发的视觉拆解、导出和模型调用验证

但它不适合承载正式多人并发处理，尤其不适合同时跑多个视觉重处理或批量导出任务。

### 5.2 初期可用策略

在 `4核 / 8G` 下建议采用保守策略：

- 重任务串行执行
- 导出任务一次只跑一个
- 用户操作和后台处理分开
- 夜间批量导入，不和白天人工审核抢资源
- 结果优先落盘，前端只查状态和展示结果

这能保证初期开发环境不因为重任务而频繁崩掉。

### 5.3 后续正式资源方向

如果按常规 `18人左右` 使用、峰值按 `30~50人` 设计，正式环境需要把控制面和处理面拆开。

建议方向：

- Web/API 服务：承接用户操作、审核、查询和导出请求创建
- Worker 服务：承接视觉拆解、模型调用、重跑、导出等重任务
- 数据库：承接 run/job/artifact/revision/review/source_tree/task 等事实数据
- 队列：承接异步任务、夜间批处理和失败重试
- 文件/对象存储：承接原始资料、页面图、题块截图、导出结果
- Cloudflare：承接初期访问控制和安全入口

正式环境不建议把所有重处理都压在 Web 服务里，否则一批导入或导出就可能影响日常审核操作。
