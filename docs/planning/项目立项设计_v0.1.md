# 讲义加工与题目治理项目说明

## 1. 项目定位

本项目围绕“讲义资料”和“题目资料”两类核心对象，建设一套统一的加工底座。

它要解决的不是单次处理问题，而是把资料加工、题目挂接和后续教研判断逐步沉淀成可复用能力。对业务来说，当前最直接的价值主要体现在三点：

- 标准讲义可以稳定沉淀，避免每次从零整理
- 老师补充题目可以纳入统一结构，减少零散管理
- 后续学科规则、考点映射和人工校核可以建立在同一底座上

## 2. 当前纳入范围

- 资料来源：标准讲义资料、老师补充题目、教师版与学生版配套资料
- 加工结果：讲义结构、组件沉淀、题目挂接、考点映射、审核结果、导出内容
- 参与角色：老师、审核人、管理者

当前阶段的重点，是先把主链路稳定下来，形成一版可验证、可复用、可继续扩展的基础能力。

## 3. 业务处理流程

![处理流程](report_assets/brd_figures/figma_process_linked.png)

- 资料统一接入，区分标准讲义与老师补充题目
- 页面拆解后沉淀为可复用组件
- 在稳定讲义结构下完成题目挂接
- 结合学科规则与考点映射进入人工校核
- 最终形成可导出、可展示、可持续复用的内容成果

这条链路里，当前有三个基本原则：

- 讲义结构单独保存，作为题目主归属的稳定底座
- 组件层单独沉淀，服务后续结构调整与内容重组
- 考点映射独立管理，承接不同学科的判断差异

## 4. 整体结构架构

![整体结构架构](report_assets/brd_figures/figma_structure_architecture.png)

整体上建议拆成五层，目的不是增加技术复杂度，而是把资料入口、内容加工、教研判断和底层支撑分开，减少相互牵连。

- 资料入口层：统一接收标准讲义、老师补充题目和配套资料
- 内容加工层：完成页面拆解、组件沉淀、结构编排和题目挂接
- 教研判断层：承接学科规则、考点映射和人工校核标准
- 业务操作层：支持结构调整、人工校核和成果导出
- 基础支撑层：提供视觉识别、任务调度、数据存储、文件存储和访问安全

这样拆开以后，上层操作不会直接牵动底层处理，学科差异也可以通过规则层逐步扩展。

## 5. 模型与技术栈

- 视觉识别与页面理解：Doubao 1.8V
- 结构模型、考点模型和其他运行模型：评测后再确定
- 当前技术基础：Python 处理链路、Web 操作界面、导出服务、Cloudflare 访问安全

技术路线的原则很简单：先把关键环节跑稳，再逐步比较和替换模型能力，避免过早锁死方案。

## 6. 当前推进思路

- 优先把主链路做成闭环，不在初期同时铺开所有学科
- 优先保证人工可控，关键节点保留结构调整和人工校核
- 优先用单学科打样，跑通后再复制到其他学科
- 优先保持模型可替换，为后续评测和升级留出空间

## 7. 阶段安排

### 第一阶段

目标：把主链路做实。

- 打通导入、拆解、结构编排、挂题、校核、导出
- 形成一版稳定的资料加工链路
- 形成可用于讨论的页面样例、流程图和整体架构图

### 第二阶段

目标：把教研判断做深。

- 按学科补充规则
- 完善考点映射和人工调整能力
- 支持夜间导入、白天校核

### 第三阶段

目标：把运行能力做稳。

- 将高负载处理与日常操作分开
- 补齐正式运行所需的权限、安全和调度能力

## 8. 当前阶段判断重点

从当前阶段看，项目值不值得继续往下做，主要看四件事：

- 讲义结构能否稳定沉淀，成为题目挂接的主底座
- 组件层能否独立复用，支撑后续结构调整
- 学科差异能否通过规则层和映射层逐步接住
- 整条处理链路能否支撑后续资料量和学科范围继续扩大
